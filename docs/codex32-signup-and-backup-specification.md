# Codex32 Signup and Backup Specification

Status: design specification; not yet approved for production custody  
Scope: Frank account creation, master backup, and recovery  
Initial target: browser application with a 256-bit Frank master secret  
Related tracker decisions: #289, #288, #536, #655, #46, and #293

## 1. Purpose

Frank will use Codex32 to create checksummed, threshold-recoverable backups of a
portable master secret. New-account setup must prove that the user can recover
that exact secret before any account becomes durable. After deriving the
initial domain secrets, Frank must remove the master secret from application
state and must not offer to reveal it from a resident copy.

This document specifies the first implementation boundary. It does not claim
that JavaScript can forensically erase memory, that a checksum authenticates a
share, or that splitting a secret protects against a compromised setup device.

The words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative.

## 2. Decisions

The v1 design makes these choices:

1. A new account starts from a uniformly random 32-byte master secret `M`.
2. `M` is the payload protected by Codex32. It is not BIP-39 entropy and is not
   generated by hashing a mnemonic.
3. Setup produces a `k`-of-`n` Codex32 share set. Codex32 limits `k` to 2–9 and
   distinct share indices to at most 31 usable values.
4. Setup is incomplete until shares entered by the user reconstruct the exact
   `M` generated in that setup session.
5. Every durable domain root is derived from `M` through a versioned,
   domain-separated derivation registry. Raw `M` is not used as a chain key.
6. After successful verification and durable account commit, Frank discards
   `M`, all entered shares, and intermediate derivation material from its live
   state on a best-effort basis. It never deliberately persists them.
7. Recovering or extending the account later requires a recovery ceremony that
   reconstructs `M`, unless setup already derived a deliberately constrained,
   versioned domain or extension root.
8. Existing BIP-39 accounts remain on their existing recovery path. Frank does
   not silently convert a BIP-39 mnemonic to Codex32.
9. The initial release supports regular-checksum Codex32 only. Choosing a
   32-byte `M` keeps every v1 share in that supported form. Long Codex32 is a
   separate compatibility milestone.
10. The checksum is error detection and correction data, not a MAC or a proof
    that a share belongs to the user.

The default `k` and `n` remain a product decision. Code MUST NOT bury a default
inside the cryptographic package. The UI may offer an explicitly documented
preset once the product decision is made, while allowing valid advanced
choices.

## 3. Goals and non-goals

### 3.1 Goals

- Survive loss of fewer than `k` shares without weakening the entropy of `M`.
- Recover from any valid set of `k` shares from the same set.
- Detect common transcription mistakes before account derivation.
- Prevent signup from completing against an unverified or stale secret.
- Keep one authoritative secret value across generation, display, verification,
  derivation, persistence, and account activation.
- Minimize how long master material exists in the browser.
- Make backup limitations understandable before the user accepts them.
- Preserve chain independence by deriving separately labelled domain roots.
- Make the flow deterministic and testable without recording real secrets.

### 3.2 Non-goals

- Protecting `M` from malware, a malicious extension, or compromised JavaScript
  running during setup or recovery.
- Making shares revocable. Copies of an old valid threshold remain able to
  reconstruct the same secret.
- Providing social recovery, an online escrow service, or server-held shares.
- Treating the 20-bit Codex32 identifier as authentication or a globally unique
  account identifier.
- Providing plausible forensic erasure guarantees in a garbage-collected
  runtime.
- Migrating existing funded identities without domain-specific rotation or
  sweep procedures.
- Defining the aggregate identity-key construction discussed in #46. That
  construction requires its own specialist review and test vectors.
- Making Mera or another passkey provider the sole source of `M`. A passkey may
  later unlock or wrap durable local domain material as specified separately.

## 4. Secret hierarchy

### 4.1 Master secret

`M` is exactly 32 bytes sampled from the browser's operating-system-backed
cryptographic random-number generator. Generation MUST fail closed if that API
is absent, throws, returns the wrong length, or cannot fill the requested
buffer. `Math.random`, timestamps, UUIDs, user input, and remote entropy MUST
NOT contribute to or replace this operation.

No string representation of `M` may be placed in a URL, router state, DOM
attribute, accessibility label, exception, log, telemetry event, crash report,
clipboard, or persistent store.

### 4.2 Derivation registry

Frank MUST maintain a versioned registry mapping each approved purpose to an
exact derivation algorithm, label, output length, and downstream interpretation.
The registry is part of the recovery format. A stored account records its
registry version; code MUST NOT reinterpret an existing version after release.

The first integration MUST freeze this registry in a separate cryptographic
specification with cross-implementation vectors before signup is enabled. At a
minimum it must allocate distinct purposes for:

- eCash/BCH wallet root;
- EVM wallet root;
- Solana wallet root;
- messaging encryption;
- identity authentication or the future identity aggregate;
- any constrained future-extension root.

Labels MUST include a Frank protocol namespace, purpose, and version. Two
purposes MUST NOT receive the same derived bytes. Chain-facing libraries accept
only their domain root, never `M`. A generic unrestricted child key retained by
the application would defeat deletion of `M` and MUST NOT be introduced under
the name “extension root.”

The exact KDF is intentionally a blocking decision, not left to individual
callers. Implementers MUST NOT improvise a mixture of BIP-32 paths, SLIP-0010
paths, mnemonic conversion, or raw hash labels. This document can be approved
before that companion registry, but production signup cannot.

### 4.3 Stored account material

After setup, durable state may contain only what normal operation needs:

- the derivation-registry version;
- domain-specific private roots or keys approved for residency;
- corresponding public identifiers;
- Codex32 backup metadata: format version, threshold, share count, and set
  identifier;
- backup-verification time and method version; and
- an atomic setup-complete marker.

It MUST NOT contain `M`, a Codex32 secret with index `s`, any threshold share,
the temporary reconstruction buffer, or a BIP-39 rendering of `M`.

Codex32 does not solve encryption at rest. Resident domain secrets remain
sensitive and require the local vault/wrapping design tracked separately.

## 5. Codex32 profile

### 5.1 Supported format

Frank v1 uses the BIP-93 regular format with:

- human-readable part `ms`;
- a threshold digit from `2` through `9` for split backups;
- a four-character Bech32 identifier;
- distinct Bech32 share indices, never `s` for an entered threshold share;
- a 52-symbol payload encoding the 32-byte secret or share; and
- the 13-symbol regular checksum.

The share count `n` is application metadata; it is not encoded in a Codex32
share. Every exported backup package or instruction MUST state both `k` and
`n`, while recovery correctness depends on `k`, identifier, length, and unique
indices.

### 5.2 Canonicalization

BIP-93 permits an entirely lowercase or entirely uppercase string and rejects
mixed case. Frank SHOULD display uppercase for hand transcription and QR codes.
It MUST accept valid uniformly uppercase or lowercase input, normalize only
after checksum validation, and reject mixed case.

Whitespace around an entire entered share MAY be removed. Internal whitespace,
punctuation, reordered characters, and concatenated shares MUST NOT be silently
removed or guessed. A normalized value is never written back as accepted
without the user seeing which share was accepted.

The current `@frank/codex32` implementation accepts canonical lowercase only.
Uniform uppercase support and official test coverage are therefore blocking
integration work.

### 5.3 Identifier and indices

The four-character identifier MUST be generated with the same CSPRNG boundary
as `M`. Collision avoidance against locally known backup sets is useful UX but
is not a security property. The identifier MUST NOT be presented as proof of
ownership.

Share indices MUST be distinct Bech32 characters other than `s`. Their selection
MUST be deterministic from the requested `n` or sampled without bias and then
persisted only as nonsensitive backup metadata. The UI labels every physical
share with its index and never relies on display order alone.

### 5.4 Splitting and recovery

The cryptographic library MUST:

- require an explicit caller-supplied CSPRNG for splitting;
- snapshot caller inputs before validation;
- reject unsupported lengths, bad checksums, mixed sets, duplicate indices,
  invalid thresholds, invalid indices, and wrong share counts;
- recover from exactly `k` valid non-`s` shares;
- return structured error codes that reveal no secret material;
- never log or stringify caller inputs on failure; and
- pass all applicable official BIP-93 vectors plus independent negative and
  property tests.

Callers MUST NOT implement interpolation, field arithmetic, checksum checks, or
share parsing in UI code.

### 5.5 Error correction

For regular strings, BIP-93 guarantees detection of any change of up to eight
symbols and defines correction goals of up to four substitutions, eight known
erasures, or thirteen consecutive erasures. This does not cover every insertion,
deletion, transposition, truncation, or adversarial replacement.

The first release MAY ship strict validation before correction suggestions. If
correction is implemented:

- it MUST be a separate API from validation and recovery;
- it MUST return candidates without selecting one;
- the UI MUST show the complete proposed corrected share and require explicit
  confirmation or re-entry;
- it MUST NOT continue recovery automatically;
- ambiguity MUST stop the flow; and
- tests MUST cover the promised correction bound and cases outside it.

## 6. New-account signup

### 6.1 State machine

The signup state machine is:

```text
choose policy
    -> generate M and backup set
    -> present shares one at a time
    -> collect verification shares one at a time
    -> reconstruct and compare
    -> derive approved domain material
    -> atomically persist account
    -> discard master/intermediates
    -> activate account
```

There is no transition from an unverified backup to account activation.
Reloading, navigating away, closing the tab, or changing account mode before
the durable commit invalidates the ceremony and requires a fresh `M` and fresh
share set.

### 6.2 Policy selection

Before generating anything, the UI explains:

- any `k` shares recover the whole account master;
- fewer than `k` shares reveal no information about `M` under the scheme's
  assumptions;
- loss of enough shares makes master recovery impossible;
- theft of any `k` shares compromises every domain derived from `M`;
- shares should be stored in separate failure and trust domains;
- making extra copies can improve availability while increasing theft risk;
- old shares cannot be remotely revoked; and
- a compromised setup device can capture the unsplit master and all shares.

The user selects or explicitly accepts `k` and `n`. Constraints are checked at
the UI boundary and again inside the package. The UI MUST NOT suggest that
putting several shares in the same password manager or physical location is
independent redundancy.

### 6.3 Generation

`M`, identifier, and sharing randomness are generated locally. The ceremony
MUST function with application network activity disabled after required code is
loaded. Analytics, relay calls, profile publication, wallet registration, and
funding prompts remain disabled until activation.

The application computes an in-memory verification commitment to `M` using a
dedicated versioned label. That commitment is used only within the ceremony and
is discarded with `M`; it is not a password verifier and does not make a weak
secret safe.

### 6.4 Share presentation

Shares are presented one at a time. At most one plaintext share is rendered in
the document at once. Moving forward clears the previous share's text, QR
payload, copy state, and timers before rendering the next.

Each screen shows:

- set identifier, share index, and “share X of n” as separate labels;
- the complete Codex32 string;
- the threshold policy in plain language;
- warnings about screenshots, screen sharing, printers, clipboard history, and
  storing shares together; and
- an acknowledgement that the share was recorded.

Copy is optional, deliberate, and reports both success and failure without
including the share in diagnostics. Clipboard clearing after a delay MAY be
offered but MUST be described as best effort; Frank cannot reliably erase
clipboard history or another application's copy.

QR display is opt-in behind the same disclosure boundary. QR scanning code MUST
operate locally and MUST NOT upload frames.

The user may go back only if doing so does not leave multiple shares mounted or
cached. Regenerating abandons the whole set; it never replaces an individual
share inside an existing set.

### 6.5 Mandatory recovery test

After all shares have been presented, the UI hides them and selects at least
`k` distinct indices using cryptographic randomness. The user re-enters or scans
those shares one at a time. The selected positions remain stable across
rerenders but not across an abandoned ceremony.

For every entered share, the UI first displays its parsed identifier and index
and asks the user to confirm that the expected physical backup was used. The
application retains only the minimum share payloads necessary to reconstruct.

When `k` shares have been accepted, the library reconstructs `M_verify`. Signup
continues only if a constant-time comparison establishes `M_verify == M`.
Checksum validity or matching metadata alone is insufficient.

On mismatch, the account is not created. The UI does not identify one share as
correct when it cannot know that. It clears the collected inputs and lets the
user retry or abandon the whole set. Repeated unexplained mismatch SHOULD offer
regeneration, not silently create a new set under the same identifier.

Verifying one threshold subset proves that subset, not every unused share. The
UI MUST say so. A higher-assurance “verify every share” workflow MAY construct
additional `k`-share subsets so each recorded share participates in a successful
reconstruction, without displaying multiple shares simultaneously.

### 6.6 Derivation and commit

Only after exact reconstruction succeeds may setup:

1. derive all initially approved domain roots according to the frozen registry;
2. derive public recovery fingerprints and addresses needed for confirmation;
3. build one complete durable account record;
4. write that record and the setup-complete marker through an awaitable atomic
   persistence boundary;
5. read it back or otherwise obtain durable-store acknowledgement;
6. clear `M`, `M_verify`, shares, share strings, KDF intermediates, and obsolete
   component state; and
7. activate or reload into the account.

No route guard may infer completion merely from a truthy secret field. No fixed
delay may stand in for persistence acknowledgement. If the durable write fails,
setup enters a terminal error state: it neither activates nor reloads. Retrying
the same already-derived record is allowed only while its guarded ceremony
state remains intact; starting over generates a new `M`.

Profile publication and chain writes occur after local durability. If a remote
side effect is not idempotent, it needs its own resumable state rather than
causing master regeneration.

### 6.7 Cleanup limitations

Buffers holding secret bytes SHOULD be overwritten before references are
dropped. Components MUST clear reactive strings, rendered nodes, camera frames,
and clipboard-status state on forward, back, cancel, unmount, account change,
and error.

These measures reduce ordinary exposure; they do not prove erasure. Engines may
copy strings, JIT values, take crash snapshots, page memory, or retain prior DOM
state. The UI and documentation MUST not promise secure deletion.

## 7. Recovery flow

### 7.1 Entry

Recovery is an explicit trusted-device ceremony, not a login form. Frank warns
the user not to reconstruct the master on a public or borrowed device. Temporary
access on an untrusted device should use a disposable session or device key,
which is outside this specification.

The recovery route starts with no active wallet and no background network
activity. It accepts one share at a time and immediately validates framing,
case, supported length, checksum, threshold, identifier, and index.

After the first valid share, expected threshold, identifier, and length are
locked. Later inconsistent shares are rejected without replacing the active
set. Duplicate indices do not count twice. The UI shows progress by index, not
the secret text.

### 7.2 Reconstruction

At exactly `k` accepted shares, the library reconstructs a candidate `M`.
Additional shares are not opportunistically mixed into interpolation. The app
derives the versioned public recovery fingerprint and available domain public
identifiers, then asks the user to confirm them against a trusted prior record.

A valid, internally consistent, adversarially generated share set can recover a
different master. Checksums and identifiers cannot distinguish it. Therefore:

- a known account MUST compare a locally or independently authenticated public
  fingerprint before replacing active state;
- recovery into a blank install MUST display the fingerprint and derived public
  identities before any remote registration, funding, or overwrite;
- directory or relay data is corroboration only unless authenticated by a key
  already trusted independently; and
- a mismatch stops recovery without partially importing any domain.

The fingerprint format and derivation label are part of the frozen derivation
registry. It MUST be visually separated into groups and include enough bits to
make accidental collision negligible; a four-character Codex32 identifier is
not sufficient.

### 7.3 Restore commit

Once the user confirms the expected identity, Frank derives the same approved
domain material as signup and commits it atomically. It does not merge a
candidate master with an already active account. Replacing an account requires
an explicit destructive confirmation naming both old and recovered public
identities.

On success, the app discards the reconstructed master and entered shares before
normal networking resumes. On any failure, it commits nothing and clears the
ceremony.

## 8. Backup management after signup

Because `M` is absent from resident state, Frank cannot later display the master
Codex32 shares. For Codex32-backed accounts, the existing “Show recovery phrase”
action MUST be replaced with a backup-status view. It may show nonsensitive
metadata and verification history, but never claim to know whether physical
shares still exist.

To create a replacement master share set, the user must reconstruct `M` from an
existing threshold in a trusted recovery ceremony, generate a completely new
set with a fresh identifier and fresh sharing randomness, verify it, and discard
`M` again. The UI must warn that every surviving old threshold remains valid;
resharing the same `M` does not revoke old copies.

True revocation requires generating a new master and rotating or sweeping every
durable identity, wallet, and encrypted-data domain. That is a multi-domain
migration, not a Codex32 operation.

Frank MAY later back up an individual domain secret independently. Such a backup
must use a distinct purpose, identifier, UI label, and threat explanation. It
must not be described as a full-account master backup.

## 9. Legacy BIP-39 accounts

The BIP-39 import and display paths remain separate during the initial Codex32
rollout. Account records MUST contain an explicit recovery-format discriminator;
format detection from user text or key length is forbidden after import.

Frank MUST NOT:

- encode BIP-39 entropy as though it were a Codex32 master seed;
- discard a mnemonic after encoding only its entropy;
- silently convert a mnemonic through PBKDF2 and call the resulting 64 bytes an
  equivalent user backup;
- present Codex32 shares as recovering the original words; or
- overwrite a legacy account during an attempted migration.

BIP-93 describes conversion of a BIP-39-derived 512-bit BIP-32 seed as
irreversible with respect to the original words and does not recommend such
interconversion. Frank's future migration should generate a fresh `M` and use
domain-specific rotation or fund sweeps. Until those procedures exist, legacy
users keep their existing backup.

## 10. Threat model and adversarial cases

### 10.1 Compromised setup runtime

Malicious code running during generation can copy `M` before splitting, bias
randomness, replace displayed shares, or substitute derived addresses. Threshold
storage does not mitigate this. Reproducible builds, dependency controls, CSP,
offline ceremonies, and eventually hardware-assisted generation are separate
defenses.

### 10.2 Share theft and collusion

An attacker with fewer than `k` honest shares should learn nothing about `M`
from the sharing construction. An attacker with `k` shares owns the master and
all domains derived from it. Location diversity must consider common operators,
cloud accounts, legal jurisdictions, disasters, and heirs, not merely different
folder names.

### 10.3 Malicious share substitution

The checksum catches accidental corruption, not a deliberate valid replacement.
An attacker able to replace `k` backups can supply a coherent different set.
Recovery fingerprints and independently known public identities detect this at
restore time only if the user has a trusted comparison.

### 10.4 Partial and mixed sets

Shares from different identifiers, thresholds, payload lengths, or duplicate
indices fail before interpolation. Identifier collisions are possible, so the
recovered public fingerprint remains authoritative. No “best effort” subset
search is performed across a bag of shares because it can hide mistakes and
create denial-of-service complexity.

### 10.5 UI races and stale secrets

Changing account, action, threshold, count, route, tab ownership, or ceremony
generation invalidates every async result from the prior generation. Each
operation carries an opaque ceremony ID checked before state mutation. Late QR,
clipboard, worker, persistence, and derivation callbacks cannot repopulate a
cleared component.

Only one tab may own a setup or recovery ceremony. A second tab refuses to
continue; it does not synchronize secret material through `localStorage`,
`BroadcastChannel`, a service worker, or another durable channel.

### 10.6 Browser exposure

Secrets may leak through extensions, accessibility trees, spellcheck, input
method editors, password managers, screenshots, browser translation, clipboard
history, developer tools, crash collection, or swapped memory. Sensitive inputs
disable autocomplete, autocorrect, capitalization, spellcheck, translation,
and password-manager capture where browsers honor those attributes. This is
exposure reduction, not a guarantee.

### 10.7 Denial of service

Parsers cap input length before allocation and do not attempt unbounded
correction or combinatorial subset search. QR scanners cap frame size and parse
rate. Error messages remain actionable without reflecting attacker-controlled
strings into HTML.

## 11. Package and API requirements

The Codex32 package remains a low-level, side-effect-free library. A separate
application service owns ceremonies and persistence.

Required package operations are conceptually:

```ts
encodeSecret(secret, metadata) -> Result<Codex32String>
decodeShare(text) -> Result<DecodedShare>
splitSecret(secret, policy, randomBytes) -> Result<Codex32String[]>
recoverExact(shares) -> Result<Uint8Array>
suggestCorrections(text) -> Result<Candidate[]> // optional milestone
```

API rules:

- secret inputs and outputs use byte arrays, not hexadecimal strings;
- returned byte arrays do not alias caller-owned buffers;
- parsing returns canonical metadata separately from any secret bytes;
- errors are stable codes with localized UI mapping outside the package;
- errors never embed input strings;
- recovery requires exactly the encoded threshold count;
- abortable application work checks the ceremony ID before publishing results;
- no API accepts a hidden global RNG; and
- no package function performs storage, networking, DOM, clipboard, camera, or
  logging operations.

Before integration, the existing package needs at least: uniform-uppercase
decoding, a documented cleanup contract, official vector parity for every
supported size, fuzz/property coverage, and independent cryptographic review.
Long-checksum support is not required for v1 but unsupported strings must fail
with a distinguishable error rather than “bad checksum.”

## 12. Persistence and data model

A Codex32-backed account record needs an explicit schema version and at least:

```text
recoveryFormat: "codex32-master-v1"
derivationRegistry: <frozen version>
backup:
  threshold: k
  shareCount: n
  identifier: <canonical lowercase 4 chars>
  verifiedAt: <local timestamp>
  verificationMethod: <version>
publicRecoveryFingerprint: <versioned encoding>
domainSecrets: <approved encrypted/resident records>
setupState: "complete"
```

The record MUST NOT include share indices if doing so is unnecessary. If kept
to support backup inventory, indices are nonsensitive metadata but may reveal
the backup policy and must not be published.

The whole record becomes visible atomically. A crash cannot leave “complete”
without domain secrets, or domain secrets without the matching format and
registry version. Schema migration is copy-on-write and retains the old record
until the new one is durably verified.

## 13. Accessibility and localization

Secret values MUST NOT appear in accessible names, live-region announcements,
validation messages, element IDs, or screenshots used by tests. Screen readers
still need nonsensitive progress, index labels, error cause, and focus movement.

Every invalid state is associated programmatically with its input. Errors
distinguish at least malformed format, mixed case, unsupported length, checksum
failure, duplicate index, inconsistent set, insufficient shares, reconstruction
mismatch, and persistence failure. They never echo the share.

Focus returns predictably after a rejected share and after closing a disclosure.
All security instructions and error mappings require English/French parity at
the repository's current localization boundary.

## 14. Verification plan

### 14.1 Cryptographic package

- Every applicable official BIP-93 valid and invalid vector.
- All supported 16-, 20-, 24-, 28-, and 32-byte regular payload sizes, even
  though application v1 generates only 32 bytes.
- Uppercase acceptance, lowercase acceptance, and mixed-case rejection.
- Randomized split/recover properties across every `k` and representative `n`.
- Every `k`-subset recovery for small generated sets.
- Fewer than `k`, more than `k`, duplicate, `s` index, inconsistent metadata,
  malformed length, bad checksum, and unsupported long inputs.
- Nonzero discarded payload bits from official vectors.
- RNG failure, short return, throwing RNG, mutation, aliasing, getters, proxies,
  and oversized input.
- Cross-checks against an independent BIP-93 implementation.
- Fuzzing of decoding and recovery with bounded time and memory.

### 14.2 Signup integration

- No durable write, networking, or activation before exact recovery succeeds.
- Deterministic fake entropy proves generated, displayed, entered,
  reconstructed, derived, persisted, and activated identities agree.
- Wrong, duplicate, stale, mixed-set, and corrected-but-unconfirmed shares
  cannot advance.
- Refresh, back, route change, unmount, account-mode change, and second-tab
  contention abandon the ceremony and clear rendered material.
- Late worker, QR, clipboard, and persistence completions cannot revive it.
- Persistence remains pending until acknowledged; failure never reloads.
- Secret strings are absent from logs, notifications, snapshots, ARIA, router
  state, analytics, and durable stores.
- Success and failure clipboard feedback is deterministic and localized.
- Every supported `k`/`n` policy is validated at both boundaries.

### 14.3 Recovery integration

- Known vectors restore identical public fingerprints and domain identities.
- Fewer than `k` shares never derive or persist a domain key.
- A coherent wrong set produces a different fingerprint and cannot overwrite an
  active account without explicit identity comparison and replacement consent.
- Mixed and duplicate shares do not alter locked recovery metadata.
- Failure is all-or-nothing across domains.
- Network activity resumes only after cleanup and durable commit.

### 14.4 Human factors

Usability testing MUST include nontechnical users, keyboard-only users, screen
reader users, handwritten uppercase shares, camera scanning, one deliberately
damaged share, and recovery after a long delay with no remembered terminology.
Tests must check whether users actually distribute shares rather than merely
click through warnings.

## 15. Implementation sequence and gates

1. Freeze the master derivation registry and publish deterministic vectors.
2. Complete and independently review `@frank/codex32`, including uppercase
   input and cross-implementation tests.
3. Add versioned account storage and an awaitable atomic persistence boundary.
4. Implement the ceremony service without UI or networking dependencies.
5. Build new-account presentation and mandatory reconstruction.
6. Build recovery into an empty profile, then guarded replacement of an active
   profile.
7. Replace master export for Codex32 accounts with backup status and a
   reconstruct-to-reshare ceremony.
8. Run unit, property, fuzz, integration, accessibility, persistence-failure,
   and actual-browser tests.
9. Obtain independent cryptographic and application-security review at an exact
   commit.
10. Enable only testnet accounts behind a format-version feature gate.

Production custody remains blocked until the derivation registry, package audit,
vault threat model, recovery fingerprint, and exact signup/recovery integration
have all passed their gates.

## 16. Open decisions

- Product default for `k` and `n`, and whether advanced choices ship initially.
- The exact derivation KDF/registry and identity aggregate defined outside this
  document.
- The recovery fingerprint encoding and trusted comparison channels.
- Whether v1 verifies only a random threshold subset or requires every exported
  share to participate in a successful reconstruction.
- Whether correction suggestions ship with initial recovery or later.
- The platform-specific local vault and passkey wrapping policy.
- Hardware or air-gapped ceremony support.
- Domain-specific rotation and funded-account migration.

None of these may be silently decided by a UI component or chain adapter.
