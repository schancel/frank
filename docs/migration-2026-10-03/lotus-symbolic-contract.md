# Lotus canonical public family — revised symbolic contract for acceptance

This selects concrete defaults for the successor of supported Lotus metadata, broadcasts, replies, offerings and federation. It is a proposal for root acceptance, not an active allocation, READY claim or source permission. Source reference: reviewed current main `febcefa1874c1a323bb2a24f275ede2e7c7ae7f0`. No object identifiers are assigned. Existing types1–18, independent vendor/raffle allocations, proof sentinel, Monad directory/Forum/DM, and held258 remain unchanged.

## Selected signature and burn semantics for new writes

Use existing common transcript framing and existing primitive algorithms1 (strict DER, low-S ECDSA) and3 (May2019 BCH Schnorr, compressed SEC1). No arbitrary payload-hash verification under those algorithm names. Allocate one approved family signature domain, proposed `frank/lotus-public-signature/v1`, with empty context, installed Lotus canonical network argument and the complete original metadata, post or offering body frame. Signature entries remain outside the signed body. Every signature verifies before economic effects; no BIP340 substitution or algorithm sniffing.

Allocate the new body types' ordinary T1 content identity through the existing `frank/content-hash/v1` common transcript, taking network from validated body field0. Call this `body_hash`; it is distinct from old protobuf SHA256 and from an ordinary submission index. Metadata/post body hashes identify exact original frames. A standalone offering body contains the target post hash, contributor intent and network, so its own signature authenticates the complete new intent, not just an unrelated target digest.

Retain native Lotus chain transaction IDs, raw transaction parsing, output values and exact commitment script grammar. Each selected output remains `OP_RETURN PUSH4 STMP|POND OP_1 PUSH32 SHA256(SHA256(compressed_author_pubkey)||body_hash)`. Metadata uses STMP; posts and standalone offerings use POND. A new offering commits its own signed body_hash, whose body binds the target post. This is a deliberate new canonical commitment meaning, not a claim old votes already did so. No legacy output is converted, rebound or reburned. The native ChainAdapter still checks exact fetched raw bytes, test acceptance, actual submit outcome and AlreadyConfirmed races. Physically burned value is always the checked sum of actual selected output values, never the claimed amount or a signed negative number.

The ordinary durable request index is SHA256(the exact complete canonical submission frame); it is never signature, chain or admission authority. Storage namespaces additionally bind installed network and collection. Full original frames, author identity, raw transactions/output indices and frozen economic policy are compared before duplicate recovery. Alternate signature encoding cannot replace an existing immutable author submission merely because a body hash matches.

Canonical network naming must be frozen with allocation: a one-to-one mapping from actual configured native Lotus Net/chain descriptor to explicit canonical network strings, checked against route address network, every body and peer installation. Do not infer a Monad identifier, accept arbitrary client tag or invent an alias in source. Proposed literals are left for the allocation owner's finite registry decision, not for implementers.

## Symbolic closed shapes and supported functions

Use FRNK framing, deterministic CBOR, exact original frame retention and shared root traversal counters. A signature-bearing submission wraps a framed closed body plus compressed author/signature entries and bounded raw transaction/output-index records. Payload body kinds are symbolic only:

- Metadata body: network, signed64 timestamp_ms, signed64 ttl_ms, ordered entries. Each entry has kind, uniquely named headers sorted by exact UTF8(name,value), and data. TTL remains presentation data; it does not expire admission/history. Entry order remains signed author order.
- Post body: network, topic, signed64 author timestamp_ms, ordered entries, optional parent_post_ref, represented as an explicit origin class plus32-byte target digest. Known `post` entry data is a required typed text frame with optional title/url/message and at least one present. Preserve exact text without URL fetching. Unknown entry kinds retain literal bounded public data, never gain routing/key/payment authority.
- Offering body: network, exact target reference (explicit canonical/historical origin class plus32-byte digest), and direction. Multiple separately burned offerings may reference the same signed body; immutable submission identities and native transaction ownership distinguish them. Direction policy is below. Target must exist before any chain effect. No bodyless signature shortcut; contributor identity and its burns remain their own immutable submission.

Supported public APIs have named successors: register/fetch/update identity→metadata PUT/GET and latest-range; createBroadcast→post PUT; parentDigest/reply→parent_post_ref plus typed title/url/message; addOfferings→offering PUT; getBroadcastMessages→root/topic/subtopic public inventory with exact post GET and paged offerings. Existing headless Lotus identity and exported RegistryHandler are both migrated explicitly. No removal justified by absent app calls. Existing topic Unicode lowercase/numeric, dot/hyphen and1–10 nonempty segments remain; ancestor/root indexing remains. Parent is presentation, not acceptance/payment authority; missing parent is permitted. Hash self-reference cannot be produced by rewriting an existing signed frame.

Header duplicate rejection is selected as the deterministic successor to backend map semantics; do not overwrite based on arrival order. Empty generic kind/header/data remains permitted within allocation budgets unless the declared typed entry requires more. New writes are closed at schema1/min-reader1; future compatible projections remain governed by the active codec rules and retain original bytes, not a permissive JSON fallback.

## Selected offering policy proposed for owner acceptance

Preserve actual native positive burn as the economic quantity and current positive offering capability. Add explicitly signed social direction for the exported negative offering capability: proposed direction enum `support` or `oppose`. Both directions burn real nonnegative Lotus value through the same OP_1 grammar and contributor-bound new offering hash. `total_burned` is checked physical sum; `support_burned` and `oppose_burned` are separate checked aggregates; display score is support minus oppose using an explicitly bounded signed representation. Direction never negates output value, refunds payment, grants authority or reuses Monad type11.

This repairs an actual client/server mismatch: exported old RegistryHandler OP_0 negative votes were not accepted by live native OP_1 validation. It is a proposed successor policy, not historical conformance. Owner acceptance must explicitly choose this signed-direction successor (recommended for full functionality) or narrowly disposition the old negative API. Default amount rule preserves existing actual-output behavior, including zero where currently valid; adding a minimum burn is not inferred. Optional positive claimed amount must match actual sum; zero/absent means computed quantity. Negative claimed amounts are not a direction encoding.

Freeze global dedup by native Lotus transaction ID plus exact raw bytes and target relationship, retaining selected-output ownership semantics; never silently double-count a transaction by changing author wrapper or direction. Contributor records remain separate; no supplemental burns attached to a reconstructed original author's signed wrapper.

## Historical public history, selected trust boundary

Historical records remain readable through plain canonical relay-authenticated projections. A historical projection explicitly states `historical_legacy_projection`, original legacy digest, retained author identity, relay-observed timestamps, parsed public metadata/post text/parent presentation and checked existing burn totals/evidence. It is served only over the installed authenticated relay HTTPS channel. It has no newly invented author signature; TLS authenticates the presenting relay. It cannot establish that the newly encoded content was independently authorized by the old author.

Old author signature/burn evidence may prove claims about the old digest, never about projected new bytes. Historical identifiers occupy a separate explicit origin class; they are not canonical body hashes or eligibility for new metadata replacement. Canonical offering references may name a historical target only if the allocation explicitly represents that target origin and the server's historical public owner already recognizes it; do not conflate identical32-byte values from different digest classes.

No original protobuf payload/frame is transmitted as opaque data on normal public routes. Exact old private records remain retained under a narrowly private historical/pending reconciliation owner; no re-signing, re-burning, reset, public decode fallback or private record exposure. Relay-local historical projection may be recreated deterministically from retained private originals and checked old evidence. Historic pending economic requests reconcile their original bytes rather than becoming canonical new writes. Historical trust classification must be shown to callers, not dropped by UI normalization.

## Bounded inventory, exact retrieval and supplements

Choose bounded inventory references plus exact single-object GET, not recursive full observations.

Inventory pages contain bounded descriptors: origin class, exact object/request hash, collection kind, durable sequence, relay-observed timestamp, optional author/address/topic and opaque next cursor. They do not embed full submissions. Exact GET returns the original immutable canonical submission frame, up to the complete root wire limit, without an extra outer record wrapper. Exact historical GET returns one bounded historical projection. The allocation must cap per-submission framing/raw parts under the root limit before ownership; maximum accepted canonical object remains retrievable unchanged.

Offerings are separately paged immutable reference inventories by exact target, with exact GET for each offering. A bounded target summary returns aggregate physical/support/oppose quantities and immutable snapshot revision; it does not embed every offering. Thus arbitrarily many retained offerings can be retrieved in finite pages without an ever-growing single observation. Large parsed historical data is represented by bounded entry references with exact retrieval, or an accepted projection cap; never truncate silently or produce an accepted-but-unservable projection.

Each page shares the existing complete root byte/item/depth budgets, max100 descriptor entries initially. Page byte budget includes complete framing and logical cursor header charge if headers are used; prefer cursor within the canonical page frame. At least one descriptor fits or explicit413. Read unknown-length streams under actual byte cap before decoder allocation; staged records/cursors publish only after complete validation. Exact GET is bounded independently. Multi-page callers require finite aggregate record/byte limits.

For federation choose durable immutable event sequence and a snapshot ceiling, not mutable latest-only timestamps. Per-peer cursor binds installed network, collection/filter, lineage/epoch, fixed snapshot ceiling and last durable sequence. Server assigns sequence transactionally with acceptance. Restart/head lineage mismatch is explicit restart/reconciliation, never silent cursor advancement. Latest metadata views remain separate derived indexes with timestamp/address tie ordering; replacement during catchup cannot erase an event before its peer processes it. Initial default snapshot age/capacity is a finite owner configuration decision; no unbounded retained copies or economic age eviction.

## User POP and authenticated replication, selected policy

Preserve ordinary user metadata PUT's existing POP policy: target-address-scoped relay-local bearer token or verified configured Monad payment; disabled and misconfigured remain different. Canonical bodies/CBOR errors do not change POP token issuance/header/payment minimum/recipient rules. Lotus burn is not POP proof. No automatic second-relay user payment.

Accept one explicit installed authenticated replication-only peer capability for both catchup and push. It formalizes current pull's direct public-store path and makes push reliable under POP-enabled peers. The capability is configured with exact source peer identity, destination origin/TLS identity and installed Lotus network. Destination authenticates the sender through a concrete installed credential mechanism, recommended mutual TLS with exact installed client identity (or another separately frozen signed request mechanism). Server TLS verification alone and Origin are insufficient sender authentication. Public discovery is only a hint and cannot install credentials.

The replication capability can inventory/read/apply ONLY public metadata/post/offering/historical descriptors and canonical submissions. Destination still performs the same normal author, network, full-byte/raw and native burn validation before accepting a new canonical economic event. It never issues a user POP bearer token, authorizes private DM/Monad profile access, bypasses burn verification or treats another relay's delivered assertion as financial finality. Historical projections stay explicitly relay-authenticated read-only; receiving one does not upgrade it into a new economic submission.

Keep PublicFederationStore's private wrapper and compile-time absence of profile/mailbox/Db unwrap. Add explicit public methods rather than passing Registry into peer code. Durable peer requests freeze exact destination generation and immutable object identities; retry remains same request/target after network uncertainty. Destination ACK means durable exact public acceptance, not a new chain transaction or finality guarantee. Bloom known-payload filters and unsigned Origin may remain performance hints only, never correctness or admission. No arbitrary caller URL/open proxy or redirect.
