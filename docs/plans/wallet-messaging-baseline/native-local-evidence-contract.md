## Failure and accepted outcome

`EvmLegacyConsolidator.applySync` currently emits an outgoing sync item without raw bytes and with `spentInputs.valueWei = transaction.value + actual fee`. The chain callback applies that item locally before sending it to the self mailbox. For a matching pool row without a spend checkpoint, `processSyncTransaction` writes an empty raw transaction and that fee-inclusive value, then marks the row spent. Level writes begin immediately. The semantic validator requires canonical signed bytes, matching hash/sender, and checkpoint value equal to transaction value alone. A subsequent unsupported self-message cannot undo the mutation; retry skips an existing checkpoint. Adding raw bytes to the item alone would still store the wrong value.

Pool accounts are reachable sources for single-source native/legacy payments and fan-in members. Main/identity-only payments do not exercise this pool-row defect. Initial native broadcast normally requires later observation/resume before this local application runs. Existing exact signed native journal evidence survives the defect; this is not evidence of a lost payment or permission to pay again.

Outcome: after the original native member has admissible successful-inclusion evidence, its existing pool state can receive a valid, durable, repeatable local transition derived from that member. Local errors remain observable and held. Remote wallet-sync remains explicitly unsupported; local success does not claim remote delivery or overall synchronization success.

## Local capability and evidence rules

The internal bound capability has the semantic shape `applyNativeMember(lifetime, operationId, memberIndex): Promise<LocalNativeApplication>`. A caller supplies identifiers and its existing lifetime, never a row, receipt, raw bytes, address exemption, or serialized message. The bundle resolves the current member from its own journal. The result distinguishes a newly committed pool transition, an already-applied exact transition, and an explicitly non-pool source; failures throw/hold. No result is a remote sync receipt.

Before mutation, validate the live wallet generation and economic/canonical-chain binding, actual operation/member existence, uncancelled ownership, signed canonical bytes and their equality with the frozen unsigned transaction, transaction hash, custody source address/index, sender/nonce/native chain, and the journal's successful-inclusion observation bound to that exact member. Use existing journal validation rather than another stored evidence representation. Pending, missing, unknown, reverted, unsigned, foreign, or stale evidence authorizes no pool transition. This is application of the journal's existing observation, not a new finality rule or an RPC refresh under the mutation lock.

For `source.kind === 'spend'`, resolve the exact existing index and verify its address/custody relation. Do not scan for an address match or recreate a missing/compacted row. Derive `lifecycle.spend.rawTx`, hash and **transaction value excluding fees** from the journal transaction; fee/debit observations stay journal-owned. Preserve funding and other legitimate record facts. Commit the valid checkpoint and appropriate existing terminal status together in one owner row update, not a temporarily invalid checkpoint-only row followed by another write. Publish derived eligibility consistently; do not trigger funding, transport, signing or maintenance as part of applying evidence.

An existing valid exact matching checkpoint and terminal state is idempotent. A different checkpoint, malformed checkpoint, contradictory status/provenance, or missing source row remains held unchanged; this small repair does not select between historical authorizations or replace earlier spend history. In particular, existing malformed records produced by the old path are not silently repaired on retry. Any residual-at-next-nonce case requiring a different prior checkpoint's disposition needs an explicit successor contract; this restriction does not erase or release either operation.

For main, identity, stealth and change sources, validate the original member/binding and return the explicit non-pool result without manufacturing a pool row or changing unrelated inventory. This contract fixes pool checkpoint provenance; it does not certify every family/inventory transition. In fan-in, apply only members with their own successful evidence; one successful member never authorizes applying a missing/reverted peer or dependent drain.

## Commit, failure and lifecycle

Run evidence recheck and the local durable transition under the existing short owner mutation mechanism, with the Stage A lock order. Hold no network/signing/transport await there. Keep the captured lifetime tracked through completion; close fences new work and drains necessary local writes. Concurrent application of one member must be idempotent and must not race an incompatible owner transition.

Await the actual local durable write before reporting local success or invoking transport. A failed/ambiguous write must remain observable, prevent a success acknowledgement, and use the existing owner's uncertainty fence until reopen resolves its state. Do not release the source or retry a payment. A successful commit followed by a crash or transport error is retried from the same member; it must verify the existing exact checkpoint and perform no new financial action.

Keep the existing `syncApplied` meaning: it may be marked only after the complete configured callback sequence succeeds. Do not reinterpret it as local-only completion or add a second persistent local-applied flag. The exact pool checkpoint is sufficient for local idempotence; the native journal remains payment/recovery authority. With current unsupported wire transport, local application can succeed while `syncApplied` stays false and the original operation reports sync pending. Do not serialize local authority into the outgoing item or add an ad hoc text encoding to make transport succeed.

A fan-in can have a locally committed prefix and then fail. Retain every original signed member and every committed local checkpoint. Report the failure; on retry verify the prefix idempotently and continue only eligible members. No compensation deletion, all-or-nothing claim across stores, fresh signing/submission, or silent success after a dispatcher warning.
