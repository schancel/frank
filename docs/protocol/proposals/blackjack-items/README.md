Before promotion, 18 remains a **proposal reservation**, not permission for active writers to emit it. Coordinate that reservation with other allocation authors before their activation; a new conflicting reservation is a dispatch blocker, not a reason to silently pick another number.

Old readers without type 18 follow existing V6 retention: exact opaque bytes in an open item slot; root retention only when explicitly allowed. They cannot execute game semantics. Required-type mismatches remain errors. An unknown or unsupported item never becomes JSON, a synthetic text item, a guessed game action, or a trigger for CBC/protobuf fallback.

For compatible future envelopes with `schema_version > 1` and a reader-compatible minimum, the schema-1 projection remains closed: only these exact shapes/keys/actions can project. New action/field semantics require a separately reviewed version/min-reader allocation. A future envelope cannot smuggle unknown fields through the closed map. Preserve original framed bytes when forwarding; never reconstruct them from a projection. Schema 1 with minimum above 1 is invalid under the existing minimum-versus-schema rule.

## 3. Exact field map, enums and nine allowed shapes

All keys below are unsigned integer keys in canonical order. No wildcard/extension map is present. Every present field must have exactly its specified type. `null`, `undefined`, empty arrays substituted for absent fields, coercion, ignored extras and defaulted required fields are forbidden. Application adapters construct fresh explicit objects, not spreads of unvalidated inputs.

| Key | Application field   | Wire representation and bound                                                                                                                                                                                                        |
| --: | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
|   0 | `gameId`            | Well-formed UTF-8 `tstr`, 1–128 bytes; preserve bytes/text exactly, no trim/NFC/case fold.                                                                                                                                           |
|   1 | `action`            | `uint`: bet=0, deal=1, hit=2, stand=3, double=4, reveal=5, welcome=6. No other value.                                                                                                                                                |
|   2 | `wagerTxHash`       | `bstr` exactly 32 bytes. Application writer accepts only `^0x[0-9a-fA-F]{64}$` (66 characters, lowercase prefix); decoder projects lowercase `0x` plus 64 hex digits.                                                                |
|   3 | `doubleWagerTxHash` | Same 32-byte representation as key 2.                                                                                                                                                                                                |
|   4 | `serverSeedHash`    | `bstr` exactly 32 bytes. Application writer accepts only bare `^[0-9a-f]{64}$` (64 characters, strictly lowercase, no prefix); decoder projects the same grammar. These are the existing SHA-256 result bytes, not a new transcript. |
|   5 | `playerCards`       | Ordered array of `uint` cards 0–51. Exact action-specific count below; cumulative full hand, never a delta or set.                                                                                                                   |
|   6 | `dealerUpCard`      | One `uint` card 0–51.                                                                                                                                                                                                                |
|   7 | `dealerCards`       | Ordered array of 2–52 `uint` cards 0–51.                                                                                                                                                                                             |
|   8 | `serverSeed`        | **`tstr` of exactly 64 lowercase ASCII hex characters** (`[0-9a-f]{64}`). These 64 textual bytes, NOT the 32 decoded bytes, remain the hash input and HMAC key.                                                                      |
|   9 | `outcome`           | `uint`: player_win=0, dealer_win=1, push=2, player_blackjack=3. No other value.                                                                                                                                                      |
|  10 | `minWagerWei`       | Fixed-width 32-byte unsigned big-endian EVM quantity, with numeric value 1 through `10^40 - 1`; welcome only.                                                                                                                        |
|  11 | `maxWagerWei`       | Same representation/range, with min ≤ max.                                                                                                                                                                                           |
|  12 | `feeHintWei`        | Optional fixed-width 32-byte unsigned big-endian quantity, numeric value 0 through `10^40 - 1`. Presence of zero differs from absence.                                                                                               |
|  13 | `rules`             | Optional well-formed UTF-8 `tstr`, at most 400 UTF-16 code units AND at most 1200 UTF-8 bytes. Empty text is allowed and differs from absence.                                                                                       |

Application-to-wire hash grammar is a writer contract, not merely a description of decoded output. Both `wagerTxHash` and `doubleWagerTxHash` must be strings consisting of the lowercase literal `0x` followed by exactly 64 ASCII hex digits, with either case allowed in those digits. Validate the complete 66-character input before converting to bytes; mixed/uppercase hex digits canonicalize to lowercase on projection. Bare hashes and uppercase `0X` prefixes are rejected. `serverSeedHash` must instead be a bare string of exactly 64 lowercase ASCII hex digits; uppercase digits and either prefix are rejected, not normalized into acceptance. All three reject leading/trailing whitespace, terminal newlines, malformed/odd/wrong-length hex and non-string inputs. No trimming, prefix insertion/removal, partial hex parsing or permissive `Buffer.from(..., 'hex')` conversion may precede validation. Enforce full-string consumption and exact lengths even where a host regex `$` can match before a final newline. These rules preserve the existing application grammars without altering binary wire fields or the textual fairness transcript.

The hint representation deliberately uses existing C8 fixed-width EVM quantities rather than CBOR integers/bignum tags or an ad-hoc numeric string. It preserves the current forty-digit limit without JS-number loss. The application adapter accepts only strings containing 1–40 ASCII decimal digits, validated across the complete string BEFORE conversion, then serializes the numeric value to 32 bytes; decode uses exact decimal `BigInt.toString(10)`. Legacy leading zeroes therefore normalize only as decimal presentation, not as game identity or entropy. A 41-character decimal input is rejected even if leading zeroes make its numeric value small. No amount/hint is ever treated as on-chain evidence. Do not enlarge these hints to the full u256 range just because the wire slot has 32 bytes.

The rules bound is explicitly JavaScript's existing UTF-16 count: a BMP scalar counts one, an astral scalar counts two. Rust must count `encode_utf16()` units, not Unicode scalars. Codec/adapter reject overlong or malformed text instead of truncating it at serialization. Existing welcome display trimming/ignoring blank rules remains presentation behavior, not a mutation of retained frame bytes. Schema 1 does not permit binary seeds, uppercase seeds, arbitrary historical test seeds, or a rewrite of an already stored seed. The sole actual seed writer produces the specified 64-character form; unsupported historical local fixtures/state must be reported, not silently transformed into a different fairness transcript.

For well-formed Unicode, the 400-UTF-16-unit bound already implies at most 1200 UTF-8 bytes. Retain the explicit byte cap in the schema and test its documented boundary, but it is redundant: removing only that byte-cap guard cannot be independently exposed while the UTF-16 bound remains enforced. Do not claim an independently reachable 1200-byte guard-mutation proof.

Every row lists the **complete** permitted key set; parentheses mean individually optional only in that row:

| Concrete shape            | Complete keys       | Additional cardinality / direction meaning                                  |
| ------------------------- | ------------------- | --------------------------------------------------------------------------- |
| bet request, action 0     | 0,1,2               | Player→dealer. No value, seed or cards.                                     |
| deal response, action 1   | 0,1,4,5,6           | Dealer→player; key 5 has exactly 2 cards.                                   |
| hit request, action 2     | 0,1                 | Player→dealer.                                                              |
| hit response, action 2    | 0,1,5               | Dealer→player; key 5 has 3–52 cards.                                        |
| stand request, action 3   | 0,1                 | Player→dealer. There is no dealer stand-card response.                      |
| double request, action 4  | 0,1,3               | Player→dealer; second independent wager reference.                          |
| double response, action 4 | 0,1,5               | Dealer→player; key 5 has exactly 3 cards.                                   |

Direction is contextual, not self-declared in the payload. Key presence unambiguously distinguishes hit/double request from response. A double carrying both key 3 and key 5, or neither, is invalid. All non-welcome shapes require game ID not equal to the reserved literal `welcome`. No new sequence number, player/dealer address, wager amount, payout hash, network, commitment domain, or signature field is allocated.

Stage 8.2 (`schema`) covers closed per-shape keys, action/outcome membership, required/forbidden presence, scalar/array/string/byte lengths, ASCII-lowerhex seed grammar, and the rules UTF-16-unit bound. Stage 9 (`semantic`) covers reserved game ID versus action; unique cards within each hand and deal's up-card distinct from its player cards; and welcome numeric ranges/min≤max. Card order is preserved, never sorted. Cross-message card/deck coherence is runtime fairness validation, not codec proof. These bounds do not claim all syntactically valid 52-card arrays are reachable under blackjack rules.

## 4. Unchanged trust, fairness, ordering and economics

1. A frame and its fields establish syntax only. Sender, recipient and network come from the existing admitted/authenticated DM context; not from a game ID, greeting, an echo, a type number, or a successful parse. Keep the #696 role-separated suite-1 context and exact admitted directory/T1 checks; this allocation adds no key or derivation context.
2. Preserve exact item-array order, including `[welcome, text]`. Do not use this change to invent a new cross-message ordering, replay sequence or delivery guarantee. Retained/reloaded messages must feed the same current game transcript, scoped to the same chat and authenticated actors.
3. A bet is a reference to a separately verified chain transfer: existing lookup requires transaction and successful receipt; the dealer still checks sender, recipient and configured amount limits. This is the current receipt-status policy, not new finality/reorg protection. RPC failure is not proof of no payment. Advertising min/max/fee/rules has no authority over dealer policy.
4. Preserve the durable global consumed-wager ownership map, duplicate game-ID protection and refund claims sharing that ownership space. Replaying the same wager for another game/player must not authorize another game. Identical duplicate input cannot reroll a deck, consume another seed, issue a second payout, or discard an existing obligation.
5. Double requires the same player, eligible original two-card hand, a second distinct verified transfer to the same dealer for exactly the original wager, and durable single consumption of that second hash. A double response carries exactly one additional card and automatically stands. No split/insurance/new action is introduced. A repeated response cannot add another card or amount.
6. Preserve the existing pre-generated commitment's ordering relative to seeing the particular wager/client entropy and its atomic consumption/next-seed state change. Do not weaken that ordering, and do not claim that merely putting a commitment in a `deal` frame creates a stronger public timestamp/precommitment mechanism than the current system has.
7. Commitment is SHA-256 of the **64 ASCII seed characters**. Deck HMAC key is those same textual bytes; message is lowercase canonical `0x` wager hash plus `:0:` plus the decimal counter. Counter-mode HMAC-SHA256, first four digest bytes interpreted big-endian, current modulo Fisher–Yates, nonce 0, and existing card/rank/suit conventions are unchanged. Binary hash fields decode back to the precise lowercase strings before the current fairness functions run. No changed random construction or “improved” unbiased shuffle is part of this work.
8. Initial player cards are deck[0],deck[2], dealer cards deck[1],deck[3]. Player draws then use deck[4…]; dealer continuation starts after player draws. Dealer stands on all 17s; busts/naturals preserve the current no-additional-dealer-draw rule. Verify full commitment, player/dealer order and computed outcome on reveal. Syntax-valid wrong reveal/outcome must fail existing fairness verification, not become a trusted payout receipt.
9. Preserve existing payout math: natural 5/2 using the existing integer arithmetic, ordinary win 2×, push returns wager, loss zero, and verified double combines the two equal transfers. Preserve owed→submitting (exact signed raw transaction plus hash)→submitted→confirmed recovery. A failed/replayed reveal cannot cancel, duplicate or reconstruct an already journaled payout. No new payout protocol field is necessary.
10. Existing errors are human-readable type-17 text via `formatBlackjackError(gameId,text)`, with the historical `[game=<JSON-quoted string>]` correlation suffix. That narrow quoting of a game-ID token is NOT a general structured-game JSON tunnel. Preserve its existing UI correlation behavior. Do not serialize a `BlackjackMoveItem`, hand, payment, commitment or reveal as text/JSON under this exception, and do not allocate an eighth `error` action here.
