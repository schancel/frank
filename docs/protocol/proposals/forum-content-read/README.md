# PROPOSED Forum content, reads and operation status

This is the isolated, preproduction proposal for [#759](https://github.com/schancel/frank/issues/759), a child of #675. It allocates **nothing in the active protocol**. The owner provisionally accepted these choices for independent review, including [type-12 epoch field 10](https://github.com/schancel/frank/issues/759#issuecomment-5970448350). The checkers are offline specification fixtures, not exported codecs or runtime admission. No route, wallet lease, database, default, or protobuf reader changes here.

## Identity and content

Use the existing FRNK v1 envelope, restricted canonical CBOR, resource limits and T1/T7/T8 transcripts in `../../cbor/README.md`. Type 9 becomes schema 2/min-reader 2. Its outer fields stay network 0, exact UTF-8 topic 1 (1–512 bytes), optional parent T1 2 (32 bytes), and content bytes 3 (1–524288 bytes). Content bytes contain one canonical map: authored timestamp 0 and an ordered array of 1–64 entries at 1. Entry kind 1 at key 0 is a Forum post, with optional title 1, URL 2 and message 3. There is no other required content-local kind.

Writers omit empty optional strings. Readers accept empty and absent as the same empty display but retain their different original bytes. Preserve Unicode, URL spelling and array order; never normalize, fetch a URL, or derive authority while decoding. Existing profile limits still apply, including 262144 UTF-8 bytes per text string, aggregate item/container limits, and nesting depth. The content budget is not an exemption from those limits. Unknown fields count toward every budget. Opened nested content participates in the enclosing frame's cumulative resource accounting.

Authored seconds are signed i64 and nanoseconds are 0–999999999. Authored time affects identity but is not chain time, relay ordering, author evidence, or the current Forum display timestamp. Display uses relay first-visible time. No author, signature, nonce, topic copy, parent copy, encryption, attachment, edit, root, moderation or tombstone fields are introduced. Same exact frame means same T1; a different authored time changes T1 intentionally. Parent and vote references remain exact immutable T1 values, never logical-object identifiers. Duplicate burners select the author by the existing minimum `(block_number, transaction_index, raw transaction hash)` tuple.

Schema 2 rejects undeclared keys in the outer/content/entry maps and unknown kinds. A later compatible schema with min-reader 2 may add optional fields: retain the **whole original frame**, not a re-encoding of known fields. Its unknown entry kinds render one fixed `Unsupported content` placeholder per entry, at most 64, with no interpretation of their fields or URL loading. They still require an integer kind and a canonical bounded map. Required new semantics raise min-reader; unsupported required versions fail before display. The same containing-schema rule applies to nested maps in reads; timestamp maps remain exactly keys 0 and 1. Readers never invent a known-text interpretation for an unknown kind.

## Candidate read frames

Types 12–15 are reserved only within this proposal, schema 1/min-reader 1. All network values are exact UTF-8 network tags (1–64 bytes). All revisions, counts and chain positions are unsigned u64, represented losslessly; JavaScript `number` is unsuitable. All hashes and addresses are raw bytes, not text.

| Type | Payload fields |
| --- | --- |
| 12 single view | 0 network; 1 exact type-9 frame; 2 author address (20 bytes); 3 author's raw signed burn (1–16384 bytes); 4 transaction hash (32 bytes); 5 relay first-visible timestamp; 6 author block u64; 7 author transaction index u64; 8 signed aggregate; 9 observation revision u64; **10 store epoch (16 bytes)** |
| 13 topic page | 0 network; 1 exact topic; 2 inclusive since timestamp; 3 snapshot revision u64; 4 array of exact type-12 frames; optional 5 next cursor bytes; 6 epoch; optional 7 exact request cursor bytes |
| 14 discovery page | 0 network; 1 snapshot revision u64; 2 entries; optional 3 next cursor bytes; 4 epoch; optional 5 exact request cursor bytes. Entry: 0 exact topic; 1 post count u64; 2 relay last-activity timestamp |
| 15 operation status | 0 network; 1 exact submitted type-10/11 frame; 2 post/target T1; 3 transaction hash; 4 sender address; 5 direction (0 down/1 up); 6 burn value u64; 7 state; optional 8 confirmed block u64; optional 9 confirmed index u64; 10 observation revision u64; 11 epoch |

Signed aggregate is `{0: negative boolean, 1: 32-byte big-endian magnitude}`. Its range is `-(2^256-1)..(2^256-1)`; negative zero rejects. Reject admission before any aggregate addition would overflow that range: no saturation, wrapping, floating point, or i64 narrowing. Individual burns remain strictly positive and at most i64::MAX. Status field 6 is encoded as u64 for exact representation, but values above that admission ceiling cannot describe admitted pending/confirmed operations. The u64 maximum is valid for revisions/counts/positions, not an admitted burn.

These are relay observations over authenticated transport. They do not make the relay's claims independently true. Clients bind response network, exact query and frame type, T1, transaction bytes/hash, sender, direction and value to their request and retained operation before any display publication or economic effect. A single view's author transaction must be an admitted **up** burn for T7 of the exact nested post. It is not evidence for a different burn on the same post. T7 remains `SHA256("frank:topic-vote:v1" || u16be(network length) || network || T1)`. T8 remains exact `TPIC || 02 || direction || T7` calldata, configured chain ID/burn destination, valid signed raw transaction, and once-only consumption by transaction hash across all encodings.

The future chain adapter must derive the transaction hash, recovered sender, chain, destination, calldata direction/commitment and value from the raw signed transaction; compare with the response and retained request; and verify its successful canonical-chain observation at configured finality before claiming independently verified confirmation. Relay-only confirmation remains explicitly relay-observed. The offline fixtures inject synthetic chain facts keyed by exact raw bytes. They prove response binding, **not transaction signature recovery or chain finality**, which remain mandatory runtime-stage gates.

## Status is a tagged claim, not a receipt by shape

Interpret field 7 **before classifying fields 1–6 as observed evidence**:

| State | Meaning of 1–6 | Chain position / wallet effect |
| --- | --- | --- |
| 0 unknown | Exact request echoes, explicitly `unverified-request`; the relay has no operation observation. Sender/direction/value are supplied request assertions, even if locally syntactically plausible. | 8/9 forbidden. Never release a lease, confirm a spend, or infer rejection. |
| 1 pending | Relay observed/validated this exact submitted operation, but no final confirmation. | 8/9 forbidden. Nonterminal. |
| 2 confirmed | Relay observed this exact operation with matching transaction-derived facts. | Both 8/9 required, including valid zero. May reconcile only this exact retained operation under the client's trust/finality policy. |
| 3 rejected-before-broadcast | 1–6 are request echoes, explicitly `unverified-request`; relay claims it rejected this request before its own broadcast. | 8/9 forbidden. Does not prove absence from the chain or other relays; cannot alone release a wallet lease. |

Unknown for burn B and confirmed for burn A can refer to identical post bytes and T1. They are different operations. Unknown cannot borrow A's author/sender/payment facts. Every status must echo the exact submitted bytes and requested facts; any mismatch rejects the entire response. Request values are not promoted to observed facts by canonicality, a status integer, or post equality. Sender/value/direction/raw bytes must match the local retained intent even when the relay reports confirmed. A state-0/3 value above the admission ceiling can be echoed as unverified input; it never enters tally arithmetic.

## Bounded pagination and cursors

Pages stop at **128 rows or 4 MiB of complete encoded response**, whichever comes first. Each type-12 frame is at most 2 MiB; count every nested frame and cursor in the response budget. A maximum admitted type-9 frame (1 MiB) plus bounded burn evidence can fit a page. Reject `row-too-large` explicitly if a row cannot fit; never silently omit it. Empty pages cannot have a next cursor. A next cursor exists exactly when more snapshot rows remain and identifies the full last emitted tuple. Post order is `(relay first-visible seconds, nanos, raw T1 bytes)`; since is inclusive; continuation is strictly greater than that full tuple. Discovery order is unsigned exact UTF-8 topic bytes, without normalization or locale sorting. No timestamp-plus-one workaround.

Cursor bytes are a canonical integer-keyed map: 0 network, 1 family (13/14), 2 snapshot revision, 3 epoch, 4 last tuple; topic family additionally requires 5 exact topic and 6 inclusive since. Topic last tuple is `{0: timestamp, 1: T1}`; discovery last tuple is an exact topic string. Wire fields carry bytes; URL transport uses their unique unpadded base64url spelling (no whitespace, `=`, alternate alphabet, or nonzero padding bits). Limit decoded cursor to 2048 bytes and encoded transport to 2731 characters **before allocation/decoding**. Unknown keys, duplicate keys, malformed UTF-8, trailing bytes, non-shortest encodings and wrong types reject. Cursor schema has no optional extension allocation.

Cursors confer **no authority** and are not signed. Validate network/family/query/since/epoch/revision against the request and a retained snapshot; validate that the last tuple actually exists in that snapshot/query. A client additionally requires exact echoed request cursor bytes and a continuation equal to its last validated returned row. A forged cursor that happens to name a real tuple only seeks within a public snapshot; it cannot grant access, fabricate observations, change the snapshot, or justify declaring a complete refresh. Client refreshes start without a cursor and advance only by validated continuations; never resume a locally complete view from an untrusted supplied offset.

Concrete provisional retention policy: at most **16 global live snapshots**, each pinning at most **64 MiB** (including pinned row/index/version storage and cursor bookkeeping), and **256 MiB global pinned storage**. Snapshots expire **120 seconds after creation**, measured by the server's monotonic clock; reads never extend this deadline. Reuse a matching retained network/revision/query snapshot where possible. At capacity, expire elapsed snapshots, then reject new snapshot creation with `snapshot-capacity`; do not evict a still-live snapshot to admit another request. A query that would exceed 64 MiB fails `snapshot-too-large`; no partial success. Retain all versions needed by an admitted snapshot for its full lifetime. Implementation must account pinned storage before admission; a storage engine that cannot bound that cost cannot implement this policy by silently best-effort streaming.

Unknown, expired or restarted snapshots fail `cursor-expired`; malformed or wrong-binding cursors fail `cursor-invalid`. A fresh random epoch is created on restart/rebuild; revision never wraps within an epoch. Client staging is capped at **64 MiB complete frame bytes, 32768 rows, and 120 seconds** per refresh; failure discards staging and preserves the last complete view. At most one refresh is staged per query. Retry begins without a cursor, at most twice per user-triggered refresh, then surfaces an explicit retryable failure. These bounds are reviewable choices, not measured capacity guarantees. Discovery exceeding the query budget explicitly fails and needs a future reviewed partitioning contract rather than silently returning a prefix.

## Publication, restart and race fencing

All page rows bind the same network/topic, epoch and snapshot revision; row revisions equal the page revision. Require strict order, inclusive since, no repeated T1, no cursor cycles, and exact request-cursor echo (absent on the initial page). Publish a replacement only after the final complete page validates. Overlapping refreshes deduplicate by immutable T1. A lower revision cannot overwrite newer state in the same epoch; equal revision must describe the same snapshot content, otherwise reject inconsistency.

Type-12 standalone responses carry epoch explicitly. A client request records its current epoch and a local refresh generation. A response from another epoch cannot overwrite the current view: it triggers a bounded fresh refresh and only that fully validated refresh can install the new epoch. Increment the local generation when beginning the replacement; discard every older in-flight response, including an old-epoch standalone view arriving after the new epoch is installed. Never compare numeric revisions across epochs. An initial standalone response may be staged for display, but cannot establish a complete topic view or replace a newer accepted generation. Epoch identity is relay scoped; different relays' epochs/revisions are not compared.

## Validation and evidence

Order: frame/header/resource/canonical/version validation; schema and nested frame/content validation; network/query/type/T1 bindings; exact raw-transaction and observed economic bindings; then cursor, publication or status effects. Unsupported required semantics, duplicate keys, invalid UTF-8, non-shortest integers, trailing bytes and negative zero reject. Generic budgets are cumulative across opened objects, not reset to permit a 128-fold resource amplification.

`vectors.json` contains tagged value recipes, exact wire bytes and T1/T7 hashes. Both checkers independently encode the recipes with the existing generic canonical/frame/hash primitives and decode the resulting bytes. A Rust-built origin post and a TypeScript-built origin post are separately reconstructed in code. Local proposal schema/policy predicates exercise hostile fixtures; none is exposed through a production facade. Run from the repository root:

The fixtures cover exact content/identity, future retention, precision, status echoes versus observations, request mismatch, cursors and restart races. They do not replace production admission, persistent snapshot/rebuild tests, or browser consumer proof. Required next landings: independent review and owner promotion into normative spec/active codecs; current-behavior tests then retained-event read/status/storage implementation; complete normal post/reply/read/list/discovery/vote/reconciliation switch; finally predecessor protobuf deletion with reachability and restart/rebuild proof. #675 owns runtime/storage/tombstone/deletion completion; #718 stays blocked until normal canonical targets and reconciliation work. #60 owns pending signed-wallet authority recovery.
