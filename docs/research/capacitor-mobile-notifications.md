# Capacitor mobile app and push notifications

Research: 2026-10-11. Read-only source inspection at release-preview revision `742b08d7497e1b7ad6864a800dd1016a099b26f1`; no mobile build, device test, credential creation or publication was performed. Implementation recommendations below are proposals, not completed work.

## Recommendation

Capacitor is a plausible way to ship Frank on iOS and Android with background **visible notifications**. Reuse the web application and existing wallet/message owners, add platform custody and authentication capabilities, and add a relay push dispatcher. It is not just enabling an existing build switch. Keep PWA deployment as the immediate release path; native work has additional custody, passkey-origin and signing dependencies.

Start with generic “New message in Frank” alerts and fetch/decrypt after opening. Push should never sign, broadcast, or decide settlement. A push receipt is not proof of message delivery or payment. Native notification services are separate from browser Web Push/VAPID.

## Observed repository state

- `app/src-capacitor/package.json`: Capacitor CLI/core `^2.0.0`, iOS `2.4.4`, old Stamp/Lotus description. `capacitor.config.json` uses app ID `org.cashweb.frank` and bundled `www` assets.
- Native projects exist: iOS Podfile targets iOS 11; Android variables target/compile SDK 30 and old Firebase Messaging 20.1.2. This is an obsolete scaffold, not a current supported mobile release.
- `app/quasar.config.js` conditionally loads `app/src/boot/capacitor.ts`. That boot file uses the old `Plugins` API, forwards pause/resume to balance polling, opens external URLs, and makes `updateBadge` a no-op. There is no implemented native push registration there.
- `app/src/accounts/session.ts:996`: custody opening explicitly rejects Electron, Capacitor and Cordova in this inspected release. Separately inspected `electron-packaging` branch removes only Electron from that guard after packaged persistence checks. It still rejects Capacitor/Cordova. Electron evidence does not establish mobile WebView safety.
- `packages/account-vault/src/index.ts` creates non-extractable AES-GCM keys, stores `CryptoKey` objects and encrypted records in IndexedDB, and probes decrypt-after-read. `app/src/accounts/custody/persistence.ts` owns account-state transactions. Mobile support needs the full restart/interruption evidence, not just `crypto.subtle` feature detection.
- `app/src/accounts/mera-passkey.ts` uses Mera's WebAuthn PRF API. `rpId = location.hostname`; root is the exact 32-byte PRF result using the fixed SHA-256 salt domain `frank.mera.account-root.v1`. Changing RP, salt, or mapping can change account identity.
- `backend/cashweb/cashweb-registry/src/events/mod.rs` has a content-oblivious arrival event containing recipient address and payload hash. Its clustered implementation is **Ephemeral Core NATS**, not a durable queue. `http/monad_message_cbor.rs:122` publishes a best-effort courtesy event after inbox acceptance with a one-second timeout; it cannot guarantee mobile notifications across dispatcher downtime. No native push-token registry or APNs/FCM dispatcher was found in this inspected path.

## Native platform baseline and custody

Upgrade the isolated scaffold and plugins to a supported coherent Capacitor version; replace legacy plugin imports. The current official v8 guide requires Node 22+, Xcode 26+, iOS 15 minimum, Android Studio Otter+, Android compile/target 36 and min SDK 24. Verify compatibility with Frank's Quasar version before selecting the final baseline; these are research-time upstream requirements, not instructions to upgrade the shared development machine. [Capacitor upgrade guide](https://capacitorjs.com/docs/updating/8-0)

Two custody paths are possible:

1. **Shortest evidence-driven path:** retain the IndexedDB/non-extractable WebCrypto vault inside the bundled WebView, only after physical iOS/Android tests prove key serialization, process-kill/reopen, update/reopen, interruption recovery and storage isolation. This matches the Electron direction but does not imply hardware-backed keys or immunity to same-origin malicious JavaScript. A namespace/origin change must not strand funded accounts.
2. **Stronger native at-rest boundary:** a narrow vault bridge stores a wrapping key through iOS Keychain and Android Keystore, with encrypted records and a recoverable commit protocol under the existing custody owner. Choose lock-state accessibility, biometric/user-presence policy, backup/restore behavior and loss handling explicitly. Keystore keys can remain non-exportable, with hardware backing dependent on the device. This does not move all chain signing into Secure Enclave/Keystore automatically: Frank uses multiple chain key types and existing derivations. Neither plaintext Capacitor Preferences nor a generic plugin marketing claim is enough. [Apple Keychain](https://developer.apple.com/documentation/security/keychain-services), [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [Capacitor Preferences](https://capacitorjs.com/docs/apis/preferences)

Keep storage capability failure visible without overwriting existing records. A locked native store should explain unlocking/retry; an unsupported host should not show a retry that can never succeed.

## Mera/passkeys

The owner's successful Safari test proves the web route works; it does not prove a bundled WebView returns the same PRF bytes. First define the production RP domain and account portability policy. A locally bundled Capacitor hostname is not automatically the hosted Frank RP. Existing localhost test passkeys cannot simply be renamed to a production RP.

- iOS: Apple supports passkeys and PRF through AuthenticationServices. For app/service association, configure `webcredentials:<domain>` and serve an AASA file authorizing the team/app ID. Investigate either a correctly associated WKWebView route or a narrow native authentication bridge injected via Mera's `WebAuthnClient`. Preserve WebAuthn PRF preprocessing and result semantics; a native PRF input is not assumed interchangeable with raw JS salt. [Apple passkey setup](https://developer.apple.com/documentation/authenticationservices/connecting-to-a-service-with-passkeys), [Apple PRF update](https://developer.apple.com/documentation/updates/authenticationservices), [WKWebView authentication](https://developer.apple.com/documentation/authenticationservices/passkey-use-in-web-browsers)
- Android: the official WebView guide supports Credential Manager with AndroidX WebKit, a feature check/enabling step and Digital Asset Links association with an owned website. Generic passkey support alone does **not** prove `clientExtensionResults.prf` is returned for Frank's authenticators. Test actual create/login PRF, cross-device login and exact identity parity before claiming Mera support. [Android WebView authentication](https://developer.android.com/identity/sign-in/credential-manager-webview)

If embedded PRF is unavailable, evaluate a system-browser authentication flow with an authenticated, single-use, session-bound return channel. Never return a wallet root in a URL/deep-link or send it to the relay. This is additional protocol work, not an already supported fallback.

## Push credentials and native setup

The official Capacitor push plugin returns an **APNs token on iOS** and an **FCM registration token on Android**. They are app-installation routing tokens, not stable hardware device IDs. The plugin needs iOS Push Notifications capability and AppDelegate registration callbacks; Android needs the Firebase project's `google-services.json`. Add notification listeners before registration and implement tap handling, permission checks, channels and icons. The plugin does not implement iOS silent pushes; Android data-only callbacks do not run in killed JS processes. [Capacitor push API](https://capacitorjs.com/docs/apis/push-notifications)

| Path | Trusted server configuration | Client/platform configuration |
| --- | --- | --- |
| iOS direct APNs | APNs `.p8` signing key, key ID, Apple team ID; JWT authentication, correct APNs environment/topic | Apple app ID/bundle ID, provisioning with push entitlement, APNs token |
| Android FCM HTTP v1 | Firebase project, enabled FCM API, service identity obtaining short-lived OAuth access tokens (workload credentials preferred where available) | Matching Android package/app registration and `google-services.json`, FCM token |
| Optional FCM for iOS | Above FCM credentials plus APNs authentication configured in Firebase | Firebase Apple SDK integration obtaining an FCM token; do not pass the default plugin's APNs token to the FCM send API |

APNs and FCM sending secrets belong in backend secret management, never the frontend bundle. Public Firebase client configuration is not the server service-account private key. [Apple APNs tokens](https://developer.apple.com/help/account/capabilities/communicate-with-apns-using-authentication-tokens/), [FCM HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api), [Firebase Apple integration](https://firebase.google.com/docs/cloud-messaging/ios/get-started)

Ask for permission in context after account activation. iOS requires notification authorization for alerts; Android 13+ has runtime `POST_NOTIFICATIONS`. Handle denial, settings changes and token registration failure without blocking wallet use. [Android permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

## Relay implementation contract

1. Add a typed authenticated subscription registration/revocation API. Bind each registration to the account/relay scope, provider, app identity/environment and installation handle; include expiry, replay protection and an authenticated challenge/signature. Reuse existing authenticated-request primitives after verifying their scope. Tokens are sensitive routing data, not authentication proof. Allow several installations per account. Refresh/upsert rotations; unlink on logout/account replacement, without deleting account keys or financial journals. This is a separate durable fact with one authoritative owner.
2. Commit a durable notification outbox alongside accepted message state, or use a durable accepted-message cursor with catch-up/reconciliation. A Core NATS event can wake the worker but cannot be its only source. If JetStream is chosen, explicitly address the database-to-bus atomicity gap. Deduplicate work by message/account/subscription; retry transient errors with backoff and provider limits, expire stale alerts, and disable permanently invalid tokens. Provider acceptance does not mean the user saw it. [FCM token lifecycle](https://firebase.google.com/docs/cloud-messaging/manage-tokens)
3. Default external payload: generic title/body plus an opaque event identifier. Do not include message text, addresses, amounts, keys or unencrypted conversation subjects. Apple/Google still observe routing/timing metadata. The relay cannot resolve an encrypted thread identifier it does not know; generic tap → unlock → fetch/decrypt → route is valid. Any richer routing metadata needs an explicit privacy design.
4. After opening, resolve the actual validated message and its stable conversation identity, then navigate. Do not collapse all threads for a peer/gateway, treat the push body as trusted content, or mark a payment settled. Compute unread/badges from authoritative app state; avoid a second independent unread owner. Coalescing and stale notifications must not inflate counts.
5. Foreground deduplication suppresses duplicate system/in-app alerts. Register/reconcile independently from financial retries; preserve reservation/journal semantics on suspension and restart.

## Background behavior, distribution and acceptance

Visible push is the retention feature to implement first. Silent background execution is opportunistic: Apple explicitly does not guarantee delivery and may throttle it; force-quit affects delivery. Android notification payloads can display through the OS while the WebView is inactive, whereas extended data processing needs native lifecycle-aware work. Do not promise a permanently running wallet worker. On resume perform inbox catch-up and authorized operation reconciliation. [Apple background notifications](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app), [Android FCM delivery](https://firebase.google.com/docs/cloud-messaging/android/receive-messages)

Physical-device gates: fresh install; restore and exact identity; passkey create/login/PRF parity; two devices; locked device; foreground/background/terminated/force-stop; permissions denied/re-enabled; token rotation/reinstall; offline → reconnect; dispatcher crash → replay; duplicate/out-of-order pushes; tapping old/foreign-account/thread notifications; upgrades preserving custody; killed sends preserving journals. Test notification presentation without granting background signing capability.

Signed local device builds are the first milestone. iOS requires the selected team, signing/provisioning and entitlements; TestFlight requires App Store Connect upload, with external testing subject to beta review. Android debug APK testing can precede signed release/AAB distribution. A store release additionally needs privacy/data disclosures, export-compliance answers and review of wallet/exchange and paid-game features under current store policies. Do not assume TestFlight/public-store approval fits the hackathon deadline. [TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/), [Apple review guidelines](https://developer.apple.com/app-store/review/guidelines/)

Planning estimate, not a delivery promise: 1–2 engineer-days for a current scaffold plus real-device custody/passkey spike; 2–4 more for authenticated token registration, durable dispatcher, native alert/tap integration and focused recovery tests; another 2–4 for both-platform lifecycle/upgrade QA and distribution hardening. Roughly 5–10 engineer-days assuming credentials, devices and the selected custody path are available. A native vault or PRF compatibility blocker can add several days; store review and account enrollment are external waits. Parallelizable lanes after agreeing API/data ownership: native packaging/custody evidence, relay outbox/providers, and UI lifecycle/tap routing. Production release should wait for their combined device evidence.
