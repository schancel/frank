## Concrete failure and outcome

CanonicalMailboxStreamParams and DirectMessageClient.subscribeMailboxStream declare onRecord:void. cashweb invokes it without awaiting; canonical decoder catches only its own synchronous/awaited errors; monad-chain explicitly discards coin/self-note processing promises and ignores the consumer promise. App supplies async onRecord and streams into chats.receiveMessages without polling's recipient/cancellation lease. A rejected host persistence callback can escape as an unhandled rejection, later streamed receipts can persist beyond that failure, and queued stale-session chat work lacks the poll path's cancellation guard. This blocks safe authenticated negotiation ingestion.

Make generic onRecord return void|Promise<void>, await every forwarding layer, and route failures to the existing observable stream error/reconnect handling. No swap imports, journal/admission hooks, financial changes or new inbox owner. Actual canonical decoding/coins/self-notes remain before host delivery. Failure must stop that stream's pending delivery sequence and close its connection so polling can replay from existing durable receipts. This is not a per-record server acknowledgment protocol; do not invent one or advance cursors from callback completion alone.

## Queue and lifecycle

At cashweb WebSocket delivery boundary, maintain one active ordered delivery and a bounded pending queue. At most32 records including active; aggregate decoded delivery+context byte lengths at most CANONICAL_DM_MAX_BYTES, including active. These are local buffering limits, not changed wire protocol limits. Compare byte totals before admitting a record. Overflow reports an observable error, closes that connection and discards queued work for polling recovery. Ping/pong remains functional while callback waits. Do not serialize unrelated sends, other streams or polling behind this queue. Avoid unbounded promise chains. Reject new records after close; a closed/error stream never starts queued callbacks. Already-started async effects cannot be undone; host cancellation gates prevent later publication where available. Consume every internal rejection, while callback failure remains visible exactly once through the stream error path. Throwing error observers must not resurrect work or leak an unhandled promise.

Preserve auth, canonical identity, existing supported wire decoding and reconnect/backoff ownership. Stale replaced connections must not schedule fresh work or overwrite the active connection. Avoid duplicate onError routing at intermediate layers: consumer errors should propagate to the one delivery owner; separate existing malformed/decode handling must not silently count failed host delivery as success. Explicitly audit closure during connection establishment, queued record processing and delayed host callback. Changes required outside scope must be escalated, not guessed.

App streaming must pass the captured recipientAddress and the same cancellation predicate/queued mutation fence as polling to chats.receiveMessages. Guard captured wallet/session before and after awaited wrapper transformation and delivery; do not recapture selected account to redirect an in-flight record. Polling's durable receipt/frontier semantics remain unchanged. Prove a failed stream record can later succeed via polling and that the failed stream never persists later queued messages ahead of it. Existing polling semantics may allow a new separately connected stream after failure; do not claim global exactly-once delivery. Repeated delivery remains existing persistence dedupe's responsibility.
