# Q3b: install owned eCash durability and revoke wallet lifetime

Root-authored Tier-3 contract, base `a4183bf7` on local integration (reviewed Q3a and H0 included). Branch `feat/durable-ecash-host`; GPT-6.1 Sol medium implementation by blackjack_evidence. Independent review and combined gates required. No push, main merge, deployment, funded livechecks or deletion of user storage.

## Current and target ownership

Q3a supplies qualified explicit native/browser adapters but production still selects localStorage or implicit headless memory. EcashWallet has no owned-store closure or lifetime guard. Chronik relay close only flips a flag; session release does not close these relays, and the application cache can reuse them at the same account/revision. Initialization can automatically reconcile/rebroadcast before returning a handle. These gaps mean merely selecting the new store does not establish session-bound financial recovery.

Keep the existing ledger as the authoritative owner of eCash inputs, operations and change allocation; preserve its schema and existing native-attempt records as distinct prior obligations. Wallet owns an acquired adapter and its operation lifecycle, relay owns its opening/open wallets, session owns its relays. Application composition selects browser storage. Custody owns signing material; no swap plugin, secret storage, new inventory or messaging dependency enters this change.

## Explicit acquisition and removal

EcashWalletOptions and EcashChainConfig require exactly one of borrowed `operationStore` or owned `operationStoreFactory`. Validate both/neither before backend construction or recovery. The factory receives exact canonical `{ chainIdentifier, walletAddress }` after checkpoint verification and canonical primary-address derivation. It can return the Q3a owned store synchronously or asynchronously. Validate returned wallet affinity before use. Acquired owner closes once on initialization failure and wallet closure; a borrowed store is never closed by the wallet. Do not infer ownership merely from a close method.

Remove `defaultEcashOperationStore`, production localStorage writer selection and `createEcashChain`'s implicit Node memory fallback. Tests explicitly inject memory. Direct native callers explicitly inject Q3a native factories with an approved existing root, or a documented test-only memory store. Never select runtime storage by silently guessing the environment. Preserve `defaultNativeTransactionAttemptStore` behavior and its existing historical obligations; replacing it with empty memory is outside scope.

Add explicit factory plumbing to `openRelayUtxoChain` for Chronik. The app's `utxo-wallets.ts` selects Q3a browser storage using the existing account storage namespace `local-account-v1`, bound again to each chain/address. Electrum remains on its existing store with unchanged financial semantics. Reject a configured chainIdentifier override unequal to canonical Ecash networkId at constructor admission, rather than exposing inconsistent chain and wallet identities.

Before a browser Q3a store is admitted, inspect the exact old `frank:ecash-operations:v1:${nativeTransactionAttemptKey(binding)}` key. Any presence, even terminal-looking JSON, rejects with an explicit unsupported-old-ledger error and preserves bytes. Failed localStorage inspection also rejects; never treat it as absence. No migration, dual reader/writer, deletion, auto-reset or rollover. Put this gate at the browser adapter/factory boundary so alternate application callers do not silently bypass it. The native adapter does not inspect browser storage. Old native-attempt keys are unrelated and remain recoverable.

## Lifetime and interruption

Introduce an explicit wallet `close(): Promise<void>` whose call synchronously revokes new operations and future signing/exposure. Closure drains admitted operations/owned I/O and is idempotent; it must not close a borrowed store. A narrow external `assertActive` lifetime capability from relay is available before initialization, including checkpoint/store/backend awaits. This is a host lifetime check, not a generic service container.

Audit public methods and every relevant await: no construction/signing, stealth import, balance/handle publication, onSigned callback, rebroadcast or fresh mutation may continue using a revoked wallet. Check before external effects and after delayed dependencies. Initialization owns cleanup even when construction itself throws. Relay close revokes opening and opened wallets synchronously; late acquired stores/wallets close before the opening rejects. Wait for owned cleanup without suppressing errors.

Already initiated broadcast cannot be revoked. Preserve original signed bytes, reservations and uncertainty, and allow completion of necessary accounting for that admitted operation before closing storage. Do not classify close, timeout or rejection as proof of zero financial effect. Do not release claims or create replacement payments. Refuse additional broadcasts after revocation, including later transactions in a batch. If underlying batch submission has already begun, preserve its entire uncertainty. Distinguish lifecycle fencing from cancelling already authorized durable completion.

Initialization currently suppresses every finishInterruptedSend failure. Replace that blanket success with observable storage/lifetime failure. Expected network uncertainty may leave retained original operations and a usable wallet only when authoritative ledger health is positively reestablished; poisoned or unreadable storage must prevent publication. Use narrow existing error categories or a final authoritative health check, not error-message substring classification or catch-all empty state. Keep recovery distinct from read-only app hydration: this workflow may finish only previously authorized operations.

Session must register a relay for release before createUtxoWallet's first await. Release synchronously invokes close on every owned relay before waiting; failure/late return closes its owner and preserves error visibility. Maintain existing stealth-custody revocation. The app cache must test relay liveness before returning same-scope entries and after open, evict revoked entries, and create a new owner after same-account/revision refresh. No need to invent new account identity or route runtime effects through custody.
