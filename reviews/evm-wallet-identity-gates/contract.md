## Current and target boundary

The primary app, Qwen and BotHost all open the shared EVM wallet factory. The factory verifies canonical configuration but only its provider's cached numeric network detection currently checks upstream identity. Secondary app wrappers separately verify registry checkpoints. The actual wallet's `reobserveNativeOperations` and `watchNativeOperation` can read and apply chain evidence without fresh checkpoint qualification. Root's source trace and the shared primitive review establish these gaps; pin actual factory/poll/watch regressions before repair.

One wallet-owned qualification boundary must cover all these hosts through the existing factory and recovery methods. Protocol registry owns public identity and pinned checkpoints; host configuration owns only operator regtest checkpoints; shared `evm-rpc-identity` executes strict raw RPC probes. Wallet lifetime owns the physical request bound and rejects stale continuations. No app dependency in wallet, duplicate host algorithms, generic connection framework, persistent certificate or alternate registry.

## Frozen decisions

Add optional readonly `operatorCheckpoint` to `EvmChainConfig`, using the shared checkpoint type. It is required when the registry's applicable probe is operator-owned. Capture canonical identity, checkpoint and relay-route values for each factory/owner; caller mutation must not rebind a wallet. Preserve the existing host stamp-resolver composition (do not freeze unrelated late-bound pricing by accident). Public checkpoint data cannot be overridden. Configuration metadata inspection can remain offline; actual wallet opening must refuse missing/invalid required checkpoints before its new RPC/evidence effects.

Wire explicit operator values through the current environment loader and typed host/fixture inputs. Use `EVM_OPERATOR_CHECKPOINT_BLOCK_NUMBER` and `EVM_OPERATOR_CHECKPOINT_BLOCK_HASH` for the existing single-selected-network environment composition, with strict paired validation and public documentation. Prefer explicit typed overrides when a host already has the run checkpoint. The real regtest harness already knows block 1 from that run and supplies it to the relay; carry the same value through `openRealWallet` and restart subprocess configuration. Never discover an arbitrary fresh block and trust it as the expected checkpoint during wallet opening. Do not change any actual secret/environment file.

Qualify the actual constructed wallet provider before publishing a new handle from `createWallet`. Repeated cached-handle publication also requires a current qualification. Concurrent opening callers already share `existing.pending`; preserve that sharing and do not let one caller dispose another caller's owner. Do not add a per-caller cancellation API in this packet. Opening qualification has a bounded internal deadline; existing app session guards continue to reject/close late results. This does not claim prompt cancellation of the whole opening procedure.

Qualify before a `reobserveNativeOperations` pass can begin its gated chain reads, recorded-evidence application or resending; preserve its existing no-owner/no-work behavior where possible. Qualify before `watchNativeOperation` calls `watcher.next()` or its fallback timer/look-at-operation, because the watcher can itself read a head. A failed or expired qualification must not be represented as a successful completed recovery pass. No successful result is cached across later passes; overlapping callers may share one currently pending qualification.

Use a wallet-scoped, finite qualification wait with default 30,000ms, matching the existing reobservation I/O budget; a validated test/config override may shorten it. A logical timeout or close must return/refuse without waiting indefinitely on RPC. Retain the physical pending request until it actually settles so repeated polls cannot start unbounded requests. Late results cannot run timed-out/canceled continuations or publish a closed wallet. Do not start a second probe step after the qualification's deadline/owner revocation; do not reuse a late successful result as a certificate for a new pass. Keep this short capability outside storage and send queues. Provider destruction and existing owner cleanup remain responsible for actual resource disposal. Opening failure must remove only the failed owned cache/admission entries, close owned resources and preserve durable records; no resets or deletion.

Current opening retires unmatched local in-use pool states and flushes before provider construction. This packet establishes pre-publication and recovery-observation qualification, not pre-mutation read-only opening safety. Do not reorder all storage/custody opening or claim every financial send is newly verified. No ancestry tracking, inventory rollback, head journal, observation generation format, protocol identity change or release action.
