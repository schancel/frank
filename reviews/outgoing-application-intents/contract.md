## Outcome and ownership

Provide an atomic durable claim and one immutable completion transition for an outgoing application decision, independent of deletable chat presentation. The next swap-feature orchestrator claims before signing, saves exact signed payload before delivery, and reuses the saved message identity. This packet installs the concrete storage seam only; no signing, UI buttons, delivery, protocol changes or financial execution. No optimistic negotiation-journal mutations.

Existing MessageStore owns outgoing records and its metadata backend owns platform transactions. Extend that owner, not a separate database/service/framework. Generic storage knows bounded opaque application bytes and transport facts, not swap schemas. Feature code will validate application bytes and derive the semantic key; wallet remains authoritative for original payment/free-envelope attempts. The known successor is the actual composer/response orchestration over this API and existing `sealedMessageId` send/recovery paths.

## Public record and operations

Add cohesive types/validation alongside MessageStore (a small co-located module is permitted). A version-1 claim has exactly: `intentKey` (64 lowercase hex), `accountId` (nonempty string <=512 UTF-8 bytes), `signerKeyId` (64 lowercase hex), `messagingChainIdentifier` (exact registry ID), `recipientPublicKey` (valid compressed secp256k1 key as66 lowercase hex), `conversationId` (canonical lowercase UUID), `stampValueWei` (canonical unsigned decimal string <=uint256), `intentHex` (nonempty even lowercase hex, <=4096 decoded bytes). Include `version:1`. Feature-specific meaning stays opaque. A record is the claim plus either `{phase:'claimed'}` or `{phase:'signed', signedPayloadHex, messageId}`; signed payload is nonempty even lowercase hex <=4096 decoded bytes and messageId is canonical lowercase UUID. Reject unknown fields, invalid combinations and malformed stored values. Canonical serialization uses explicit field order; returned records are immutable copies.

Expose `claimOutgoingApplicationMessage(claim): Promise<Record>`, `completeOutgoingApplicationMessage({claim,signedPayloadHex,messageId}): Promise<Record>`, `outgoingApplicationMessage({intentKey,accountId}): Promise<Record|undefined>`, and `outgoingApplicationMessages({accountId}): Promise<readonly Record[]>`. Naming may be tightened consistently without changing semantics. Claim creates only when absent; exact repeat returns current record including signed state. Any changed claim fact conflicts before mutation. Completion requires an existing exactly matching claim; claimed -> signed is the only transition. Exact signed replay succeeds; different payload or message identity conflicts. Missing claim never gets created by completion. Reads are nonmutating, scoped and deterministic; account mismatch rejects rather than returning another account's record. List sorts by intentKey and validates every row it examines; corrupt records are observable.

Storage key is `outgoingApplicationIntent:` plus intentKey ONLY. Account, chain, signer, conversation and payload are immutable values, not extra key components. The feature successor derives intentKey privately from the protocol sender coordinate, so context/incarnation changes cannot bypass a claimed slot. This store neither derives the key nor claims distributed exclusion. Duplicate keys with conflicting owners reject. Capacity is128 retained records per accountId, independently of chat history; exact replay/completion remains possible when full. No eviction or deletion API. Enforce capacity and claim in the same serialized/atomic boundary. Do not introduce mutable competing indexes just to count128 rows.

## Durability, lifetime and format

Browser claim/complete use real strict IndexedDB transactions in the existing metadata adapter. Compare, capacity inspection, record write and first format marker belong to that transaction; no check-then-put across transactions or reliance on process-local queues for cross-tab exclusion. Native uses existing exclusive Level handle, MessageStore mutation queue and synchronous batch. Preserve LevelJS encodings. Input snapshot/validation occurs before awaits. Concurrent conflicting claims yield one winner; same-intent callers see the winner. Expected conflict/capacity refusal leaves the owner usable. An uncertain write acknowledgment poisons further mutations until close/reopen; a read-only lookup after reopen determines what committed. Do not infer absence from an error or erase the uncertain record. Close rejects newly requested work and drains previously accepted writes under existing lifecycle policy.

History `deleteMessage` and `suppressAndDelete` must not remove these records. `clear` must preserve these records and existing financial bindings plus schema marker while removing presentation/history metadata according to existing policy. No account reset implementation is included.

Advance MessageStore's format marker to3: the changed retention semantics must not be opened by a schema2 reader that could clear the new authority. Fresh absent stores stay absent on reads; first authorized mutation writes marker3. Existing marker2 is explicitly unsupported, with no migration, dual reader or automatic deletion. Update affected writers/tests consistently and document the development-only unsupported-format path without executing any reset. Preserve funded wallet/custody databases and all actual user files. Existing financial-binding and receipt durability semantics must remain intact.

Current shape: metadata schema2 has receipt/suppression/financial bindings but no pre-sign application decision. Target: schema3 adds one retained immutable decision record. Future UI adds feature semantics through public operations, not private database access. Refused framework: no workflow engine, general lease manager, second attempt ledger, key vault or feature registry.
