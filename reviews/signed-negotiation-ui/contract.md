## Identity and interruption rules

The semantic signing slot uses the protocol coordinate `(swapId, laneId=0, senderKeyId, sequence=0)` under a dedicated private account-derived domain. Conversation, role, parties, policy, chain, chosen action and exact offer commitment are immutable claim values, not escape hatches in the exclusion key. Account incarnation replacement retaining the signing identity cannot mint permission to sign an opposite response. A different recovered account ID with an existing key must fail visibly pending explicit reconciliation rather than overwrite it.

Use the existing account salt capability and canonical encoding primitives. Distinct domains separate the full-HMAC local intent key from the deterministic wire UUID. Wire identity includes the signed event commitment and validated transport context so different signed responses from independent devices cannot collapse into ordinary message revisions. Pin the exact transcript with independent vectors before dispatch. The storage `signedPayloadHex` is the exact negotiation eventHex; no wrapper JSON inside ordinary text.

Allocate one genuinely new 32-byte swap ID when beginning a new proposal. Keep it through the form's confirmation and retries; deliberate New offer creates another. For a response, claim the exact admitted offer and decision before the builder can invoke the signer. Matching repeated calls resume; conflicting calls reject. After signature completion, retry uses stored bytes and original wire identity. A timeout or UI deletion never releases the claim. If interrupted before completion, revalidate the saved intent and current session before any repeated signing of that identical ordinary identity-signature input. Never resume threshold/adaptor signing through this API.

New authorization requires unexpired terms. Resuming delivery of already persisted signed bytes must not silently replace expiry or sign a new offer; display expired negotiation distinctly from unfinished message delivery. An acceptance's existence does not authorize funding, and historical agreement is distinct from present eligibility.

`eventId32` is the existing protocol event ID, which commits the unsigned core. It distinguishes different decisions/context; a different valid DER representation of the same decision is not a new intent. Exact signed bytes are still immutable once completion wins. Matching concurrent signers must converge on the stored winner; never expose a losing signature or invent a second message because byte completion conflicted.

## Frozen local intent payload

The outgoing store's opaque `intentHex` is lowercase hex of canonical CBOR for this exact versioned array:

`["frank/swap-negotiation-local-intent/v1", action, swapId32, conversationId16, [partyA33, partyB33], policyName, xecChainIdentifier, evmChainIdentifier, detail]`

`action` is unsigned integer0=offer,1=accept,2=reject. For an offer, `detail` is `[xecPrincipalUint64, evmPrincipalBytes32BE, expiryUint64]`. For a response, `detail` is `[exactSignedOfferBytes]`. The latter carries the offer event ID, terms hash and amounts through the existing validated offer, so there is no second independently editable copy. Context and policy fields must exactly agree with that offer. Principals are positive, fixed-width EVM bytes are big-endian, and all array arities are exact. Require canonical decoding/full consumption, existing bounded decoder budgets, public-key validity, distinct parties and the selected fixed policy. The entire encoded intent fits the storage4096-byte limit. This is local persistence only, not a new wire message or protocol version.

Use existing public offer/response encoders, decoders and builders for their semantic validation; do not duplicate the signed negotiation schema. Before a claim or resume, verify that the local identity is the required action producer, the outer stored recipient is its counterparty, the original conversation matches, and the configured canonical messaging chain is supported. Recompute and compare intentKey/signerKeyId from the validated intent and admitted account capability. For signed completion/recovery, decode the stored event under that exact context and require its action/offer commitment/terms to match the claim, then recompute the persisted message ID. Only then reconstruct `{type:'application', itemType:'swap-negotiation-v1', value:{eventHex}}` through the composed plugin.

Keep restoration phases distinct: a claimed-but-unsigned decision may resume only the same validated authorization while eligible; a completed signature resumes exact bytes and original delivery even if eligibility later expires. Neither phase inserts authenticated journal evidence. A malformed persisted feature intent visibly blocks that intent before signing/sending; do not delete it, reinterpret it as a new proposal, or weaken application hydration errors into an empty state. The predecessor's generic record validation is necessary but cannot replace these feature checks.
